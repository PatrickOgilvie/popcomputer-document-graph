## Fixed findings

### Blocker: concurrent orphan cleanup could delete a newly published edge

- **Where:** `src/storage/postgres/runtime.ts`,
  `deleteOrphanedReferencedNodesInTransaction`.
- **Standard:** async/workflow transaction integrity and real persistence tests.
- **Proof:** removing A → B while another transaction inserted C → B allowed
  cleanup to select B as an orphan from an earlier snapshot, wait for B's lock,
  then delete B and cascade away the newly committed C → B edge. A real
  PostgreSQL reproduction returned zero edges where one was required.
- **Why it matters:** a successful concurrent publication could silently lose
  its topology.
- **Fix:** lock candidates with `FOR UPDATE SKIP LOCKED`, then recheck their
  references in a separate statement before deleting. Replacement cleanup is
  restricted to former targets. Explicit node deletion locks the node before
  counting and deleting incident edges. Locked orphans can be collected by a
  later reconciliation.

### Blocker: reciprocal topology writers acquired node locks in opposite orders

- **Where:** `src/storage/postgres/runtime.ts`, topology replacement.
- **Standard:** async/workflow concurrency ownership.
- **Proof:** concurrent A → B and B → A publications each locked their source
  before their target, producing a lock timeout/deadlock in PostgreSQL. The
  regression failed before the correction.
- **Why it matters:** otherwise valid simultaneous indexing could fail.
- **Fix:** batch source and target nodes in a shared document-key order, while
  preserving materialized nodes and self-reference semantics. Both concurrency
  regressions live in `tests/postgres-topology-concurrency.integration.test.ts`.

### Blocker: PostgreSQL ignored projection versions in pruning and mixed catalogs

- **Where:** `src/storage/postgres/runtime.ts`, `staleGraphSql` and scope SQL.
- **Standard:** domain invariants and adapter conformance.
- **Proof:** pruning kept revisions from obsolete projection versions. A
  catalog containing both versioned and unversioned entries also dropped the
  version restriction on explicitly versioned entries.
- **Why it matters:** stale projection data could survive reconciliation and
  contribute search results.
- **Fix:** match each catalog entry independently; an omitted version is a
  wildcard for that entry only. Expanded shared pruning conformance and real
  PostgreSQL semantic/text search coverage verify the behavior.

### Blocker: committed D1 replay returned newly calculated commit counts

- **Where:** `src/storage/d1/projection-publication.ts`, `loadCommittedOutcome`.
- **Standard:** durable idempotency and observable result consistency.
- **Proof:** replay could calculate counts against the already active revision
  and return those counts instead of the original persisted outcome.
- **Why it matters:** retrying the same committed mutation could change its
  reported inserted/updated counts.
- **Fix:** read the original persisted counts and token when returning
  `AlreadyCommitted`. SQLite-backed tests and the Workers runtime test verify
  replay with different proposed counts.

### Blocker: Turbopuffer mutation identities conflated absent metadata with null

- **Where:** `src/storage/turbopuffer/projection-index.ts`, `chunkPayload`.
- **Standard:** domain identity and durable idempotency.
- **Proof:** absent metadata and explicit JSON null had the same mutation
  digest despite producing different stored metadata-presence values.
- **Why it matters:** distinct publications could be treated as the same
  mutation.
- **Fix:** include metadata presence in the canonical payload. Regression
  coverage verifies different mutation IDs and payload digests.

### Should Fix: document-target filtering disabled the PostgreSQL key index

- **Where:** `src/storage/postgres/runtime.ts`, document-key scope predicate.
- **Standard:** storage boundary contracts and measured verification.
- **Proof:** casting the stored `char(64)` key to text produced a sequential
  revision scan for a single-document target. The benchmark below records the
  resulting query time.
- **Why it matters:** narrow searches scanned unrelated revision keys.
- **Fix:** compare the unchanged key column against a `char(64)[]` parameter.
  The measured plan uses `projected_revisions_pkey` and returns identical data.

### Should Fix: publication performed unnecessary reads and history scans

- **Where:** Turbopuffer `needsReusableVectors`; D1
  `cleanupProjectionMutationsStatement`.
- **Standard:** module responsibility and bounded async/storage work.
- **Proof:** Turbopuffer downloaded previous vectors even when replacements
  supplied every required embedding. D1 finalize/supersede scanned mutation
  history for unrelated document projections.
- **Why it matters:** publication cost grew with avoidable network transfer
  and unrelated workspace history.
- **Fix:** skip vector reuse queries when supplied content covers all chunks;
  constrain D1 cleanup to the affected document projection while checking
  references across all retained generations. Vector-query and history
  retention tests cover these paths.

## Performance evidence

Measured with PostgreSQL 17.8, 10,000 synthetic documents, one 1,024-dimensional
chunk per document, JIT disabled, one warmup and five measured runs per query.
Query order alternated between iterations. Times are medians from
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`.

| Isolated query change | Previous | Updated | Speedup |
| --- | ---: | ---: | ---: |
| Exhaustive cosine: positional join → paired expansion | 3,638.802 ms | 1,359.357 ms | 2.68× |
| Single-document target: column cast → native key comparison | 2.008 ms | 0.194 ms | 10.35× |

The second comparison uses the optimized cosine expression on both sides to
isolate key filtering. All returned rows, scores, and ordering were identical
within each comparison. The indexed target changed the revision-table plan
from a sequential scan to a primary-key index scan.

These measurements support the query improvements on this fixture. They do
not establish production latency or an ANN-scale capacity claim: unrestricted
PostgreSQL semantic retrieval still scores every eligible chunk, and these
timings exclude embedding and network costs. No numerical speedup is claimed
for D1 or Turbopuffer without live latency measurements.

Reproduce from a source checkout:

```sh
bun run build
TEST_DATABASE_URL=postgresql://localhost/document_graph_test \
  node benchmarks/postgres-semantic.mjs
```

The script generates temporary data, reconstructs the previous SQL expression
within the current production query, checks result equality, prints timings
and plans, and rolls back. Recorded samples and scan summaries are in
[`0.4.0-postgres-benchmark.json`](./0.4.0-postgres-benchmark.json).

## Verification and release preparation

`bun run verify` passed with PostgreSQL integration enabled against an isolated
PostgreSQL 17.8 instance:

- Lint, source types, consumer type tests, and package build passed.
- Bun: 238 passed, one skipped, zero failures; 945 assertions across 34 files.
- Cloudflare Workers runtime: one test passed.
- Node.js 22.22.2 ESM package smoke test passed.
- The reproducible PostgreSQL benchmark passed both result-equality checks.

The skipped test is live Turbopuffer conformance. The local protocol suites
exercise publication, search, retries, and provider constraints, but do not
replace verification against a deployed provider. With a disposable deployment
configured as described in the README, run `bun run test:live:turbopuffer`
before publishing if live provider verification is required for this release.
