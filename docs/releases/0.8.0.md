# @popcomputer/document-graph 0.8.0

v0.8.0 runs Turbopuffer retrieval beside PostgreSQL topology. PostgreSQL keeps
graph topology and the publication journal; chunks, vectors and full-text
indexes live in Turbopuffer.

## Why

A production catalogue in PostgreSQL held about 950 MB of embeddings and a
321 MB HNSW index in a 2 GB database. Agency-profile searches shared that one
index with case-study chunks, so a profile search scanned past case studies
and took 0.2 to 5 s. Until now the Turbopuffer adapter could only coordinate
publications through D1, which would have split topology across two
databases.

## Added

- **PostgreSQL publication journal.** `postgresProjectionPublicationCoordinator`
  stores the journal in PostgreSQL, created by migration 0006.
  - Each transition runs in one pool transaction that locks the head row.
  - Rejected publications roll back, so they leave no staged rows.
  - Its behaviour matches the D1 coordinator: a shared conformance suite runs
    against both.
- **Composition.** `makeTurbopufferPostgresDocumentGraph` provides PostgreSQL
  topology plus Turbopuffer index, semantic, text and hybrid search.
  `turbopufferProviderStorage` pairs Turbopuffer with any journal.
- **Copying an existing index.** `copyPostgresProjectionIndex` copies a graph's
  PostgreSQL projection index into any `ProjectionIndexStore`, reusing every
  stored vector, so nothing is re-embedded.
  - It pages in document-key order.
  - It skips revisions the target already holds, so a copy resumes cheaply.
  - `readPostgresProjectionIndexPage` exposes the reader on its own.
- **Bulk writes.** `coalesceWrites` lets publications that arrive together
  share one provider write.
  - Turbopuffer applies conditional writes one at a time per namespace, so
    without it a bulk copy publishes about eight documents a second.
  - Every row keeps its own generation fence.
  - Each publication confirms its own rows from the affected IDs; one that
    cannot reconciles its marker as before.
- **Request compression.** `compression` on the Turbopuffer client gzips
  request bodies, for bulk writes limited by upload bandwidth.
- **Half-precision vectors.** `vectorElementType: "f16"` on Turbopuffer
  partitions.
- **Web-search syntax in Turbopuffer text search.**
  - BM25 ranks every positive word.
  - A query made of quoted phrases, such as `"food photography" OR "recipe
    video"`, also requires one alternative's phrases, matching PostgreSQL's
    `websearch_to_tsquery`.

- **Search without the journal.** `candidateVerification: "provider"` makes
  Turbopuffer search trust live rows. Every publication writes a document's
  marker, live slots and tombstones in one fenced request, so live rows are
  always a complete revision. Search then needs no PostgreSQL connection
  except for topology.
- **One request per search.** `coalesceSearches` packs searches that arrive
  together into multi-queries of up to 16 subqueries. Turbopuffer ran a
  12-subquery multi-query in about 60 ms of server time.
- **Wider candidate pools.** `chunksPerDocument` caps one document's chunks in
  a channel, through `limit.per` on `document_key`.
- **Cache warming.** `warmCache` loads a namespace into cache. A namespace
  idle for hours answers its first query in about 1.5 s.

## Changed

- **Breaking: new namespaces.** Turbopuffer namespace identities include the
  vector element type, so existing partitions map to new namespaces and journal
  generations. Republish, or copy from PostgreSQL.
- **Breaking: base64 vectors.** Publication writes send vectors as base64
  little-endian float32, about a quarter the size of JSON numbers.
- **Smaller search transfers.** The client asks for gzipped responses
  (`compressResponses`, default on). Query vectors go as base64, a quarter of
  their JSON size. One 240-row query fell from 111 KB to 26 KB on the wire.
- **English text search.** English Turbopuffer full-text fields stem words and
  drop stopwords, like PostgreSQL's `english` configuration; Turbopuffer
  defaults both off. Existing namespaces rebuild those indexes in place.

## Upgrade

- Apply PostgreSQL migration 0006 before using the PostgreSQL journal.
- D1 workspaces need no migration, but they publish into new namespaces.

## Verification

- 292 unit tests pass, plus the Workers runtime test and the Node ESM smoke
  test.
- The 16 PostgreSQL journal tests (14 shared conformance cases plus 2
  PostgreSQL-only cases) and the index copy test pass on PostgreSQL 17.
- Live copy of a production catalogue from a laptop: 41,708 revisions in 31
  minutes, every one active in the journal and none pending.
  - One write per document: about 8 documents a second.
  - With write coalescing, base64 vectors and compression: about 25 a second.
- On that catalogue, 20 real matchmaker searches, 3 rounds each, with the same
  query vectors on both stores (query embedding excluded):

  | | p50 | p90 | max |
  |---|---|---|---|
  | PostgreSQL | 1,993 ms | 2,892 ms | 3,327 ms |
  | PostgreSQL + Turbopuffer | 680 ms | 1,144 ms | 1,831 ms |

- Vector parity: for stored chunk vectors used as queries, the top hit matched
  in 8 of 8 searches, and 94% of each top 30 was shared.
