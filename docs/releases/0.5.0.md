v0.5.0 adds approximate PostgreSQL semantic search through a pgvector HNSW
expression index, and server-side search timeouts.

## Why

Exhaustive search reads every embedding in scope. On a production catalogue of
120k 1,024-dimension chunks (about 950 MB of TOASTed float64 arrays) on a small
instance, one semantic search read the table from disk and ran past 16 seconds,
and searches kept running after their callers gave up.

## Added

- `vectorSearch: { mode: "approximate", index, dimensions }`: whole-graph
  candidates come from an HNSW index with scope applied during the scan, then
  are rescored exactly in float64, so scores and ties match `"float64"`
  search. Everything else keeps exhaustive `"auto"` scoring, as does any
  search while the index is missing, building, or invalid.
- `postgresVectorIndexSql()`: the matching `CREATE INDEX CONCURRENTLY`
  statement over the existing float64 column. No column, rewrite, or backfill.
- `searchTimeoutMilliseconds`: `statement_timeout` for each semantic and text
  search.
- Migration `0005_native_halfvec_eligibility.sql`: the halfvec range guard used
  by the halfvec index predicate.
- `search(query, { textQuery })` on graph retrieval: a separate full-text query,
  such as quoted key phrases joined with OR, while semantic channels still
  embed `query`.
- `textSearchTimeoutMilliseconds`: best-effort text search. A text search
  cancelled at this budget returns no candidates and hybrid retrieval continues
  on its semantic channel.

## Changed

- PostgreSQL text search ranks matches on the stored combined vector first and
  weighs only the best four per requested candidate exactly. On the production
  catalogue a four-phrase OR query fell from over 8 seconds to about 0.4.

## Upgrade

Apply migration 0005. It only creates a function. Nothing changes until an
application opts in to `vectorSearch: { mode: "approximate" }` or
`searchTimeoutMilliseconds`; existing configurations issue the same statements
as 0.4.1.

To enable approximate search, build the index outside a transaction, confirm it
is valid, then switch the configuration:

```sql
SELECT indisvalid, indisready FROM pg_index WHERE indexrelid = '<schema>.<index>'::regclass;
```

```sh
npm install @popcomputer/document-graph@0.5.0
```

## Verification

- 261 Bun tests passed with live suites disabled.
- Against PostgreSQL 18.2 with pgvector 0.8.1: 274 tests passed, including all
  existing PostgreSQL and pgvector integration suites and the new HNSW suite.
  Only the live Turbopuffer suite was skipped.
- The HNSW suite (2,200 64-dimension unit vectors across two graphs and two
  projections) confirms the adapter's statement plans as an HNSW index scan,
  approximate top-24 recall of 0.998 against exhaustive search over 20
  queries, scores identical to exhaustive float64 search for shared
  candidates, projection and graph scope preserved with a 20% selective scope
  still returning full pages, and out-of-halfvec-range vectors remaining
  writable.
- Unit coverage for `textQuery` routing, the two-phase text statement, and
  best-effort text timeouts (only SQLSTATE 57014 is tolerated; the code was
  confirmed against PostgreSQL 18.2).
- Lint, source and consumer type checks passed.
