v0.4.0 makes graph retrieval faster, adds Cloudflare D1 + Turbopuffer storage, and fixes concurrent publication and topology consistency failures. Direct document matches and related-document evidence continue to contribute independently to the final ranking.

## Faster retrieval

- Relationship expansion batches up to 100 source documents per read across PostgreSQL, D1 and in-memory storage, preserving per-source limits, ordering and evidence provenance.
- PostgreSQL automatically selects pgvector when the executing role can access it. Otherwise it uses the extension-free float64 scorer. Both paths apply scope filters before candidate limits and perform exhaustive search.
- Float64 cosine search computes the query norm once; plain-text ranking reuses stored full-text vectors. Document-key filters use the indexed native key type.
- Turbopuffer skips downloading previous vectors when a replacement supplies every embedding. D1 publication cleanup only scans the affected document projection's history.

On a local fixture with 1,000 Agencies, 9,000 CaseStudies and 1,024-dimensional embeddings, native hybrid retrieval improved from **1,074.9 ms to 106.6 ms (10.1×)** and lexical retrieval from **24.8 ms to 11.1 ms (2.2×)**. Hybrid retrieval uses **five database statements instead of 104**, plus an initial pgvector capability lookup. Float64 hybrid retrieval improved to 953.4 ms.

These synthetic measurements exclude embedding API latency. Native float32 scores can reorder near ties. See the [benchmark method and results](https://github.com/PatrickOgilvie/popcomputer-document-graph/blob/v0.4.0/docs/experiments/agency-retrieval-production-2026-09-07.md).

## New capabilities

- Canonical referenced and materialized graph nodes, node pagination, related-node queries and bounded relation-constrained search.
- D1 topology and durable publication coordination, including generation fencing, exact committed replay and bounded publication history.
- Turbopuffer semantic, lexical and hybrid retrieval with workspace partitioning, pinned schema generations and provider-aware retries.
- `makeTurbopufferD1Workspace` for composing workspace storage, an exported D1 Drizzle schema, and a strict `PreparedGraphMutationArtifact` codec for durable replay without recomputing embeddings.

## Correctness fixes

- Concurrent orphan cleanup no longer deletes newly published PostgreSQL edges; reciprocal topology writers acquire node locks consistently.
- Reconciliation and mixed projection catalogs enforce each projection's version independently.
- Rejected duplicate Turbopuffer requests preserve shared publication authority so another in-flight attempt can finalize. Retry the exact prepared mutation after resolving the request failure.
- D1 committed replay retains the original commit counts, and publication identity distinguishes absent metadata from JSON null.
- Default node listing excludes retired document kinds. Inaccessible pgvector installations use the float64 fallback.

## Upgrade notes

This pre-1.0 minor release includes breaking adapter changes:

- PostgreSQL users upgrading from v0.3.0 must apply `0003_graph_topology.sql` and `0004_native_vector_eligibility.sql` after the existing migrations. Existing embeddings remain float64 and do not need regeneration. The runtime never installs pgvector or applies migrations automatically.
- Custom topology adapters must replace `GraphRelationStore` with `GraphTopologyStore`. `findRelatedNodes` accepts `documentKeys` and returns ordered `RelatedGraphNodeSet` groups, including duplicate and empty requests, with an independent limit per source.
- Projection replacements carry `TextSearchPolicy`; registered projection catalogs carry projection versions.
- `searchWithin` requires `maximumDocuments`. Search queries are limited to 8,192 characters.
- Prepared replay can call storage providers, while reusing the captured embeddings.
- Turbopuffer partitions require a stable, non-secret deployment ID and an explicit regional or HTTPS custom endpoint.
- Native scoring uses float32 precision. Set `vectorSearch: "float64"` when exact float64 scoring is required throughout.
