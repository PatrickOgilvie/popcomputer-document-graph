# @popcomputer/document-graph 0.9.0

v0.9.0 keeps a second projection index, such as Turbopuffer, in step with the
PostgreSQL one. Applications keep writing PostgreSQL as before, and every
change reaches the mirror without the writer having to report it.

## Why

0.8.0 could copy a whole PostgreSQL index into Turbopuffer, but nothing kept
the copy current. An application whose imports and scheduled syncs write
PostgreSQL had a Turbopuffer index that went stale from the moment the copy
finished. A full copy every few minutes would read every revision each time.

## Added

- **Change set.** Migration 0007 adds `projection_changes` and a trigger on
  `projected_revisions`.
  - Inserts, replacements and deletions, including graph prunes, each mark
    their document projection in the same transaction.
  - A projection holds one row however often it changes. The set is never
    larger than the index, even when nothing drains it.
- **Mirror.** `mirrorPostgresProjectionChanges({ pool, schema, manifest })`
  drains the set into the provided `ProjectionIndexStore`.
  - A changed revision is copied with its stored vectors, so nothing is
    re-embedded.
  - A revision PostgreSQL no longer holds is deleted from the target.
  - Revisions the target already holds with the same hash are skipped.
  - Each change is cleared only after its target write succeeds. Failed
    writes are listed in `failures` and stay recorded for the next drain.
  - Every change carries a sequence renewed on each write, and clearing
    matches it, so a projection rewritten during a drain keeps its record.
  - `batchSize`, `concurrency` and `maximumBatches` bound one drain;
    `drained: false` means changes were left unread.

## Changed

- **Cheaper repeated copies.** `copyPostgresProjectionIndex` asks the target
  for each page's revision hashes before reading chunks. Only revisions the
  target lacks, or holds at another hash, load their chunks and vectors, which
  are most of a page's bytes. A catch-up copy of a 40,000-revision index that
  is already current now reads revision rows, not every vector again.

## Upgrading

Apply migration 0007, then run `copyPostgresProjectionIndex` once to catch
changes made before the trigger existed. Then schedule
`mirrorPostgresProjectionChanges`. Nothing changes for applications that do not
mirror, apart from one small row per changed projection.
